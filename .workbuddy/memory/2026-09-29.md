## 表头识别规则（`webapp/sheet_agent.py`，排查填表问题时看这里）

分两层：前三步是确定性代码规则，第四步交给 LLM，第五步是人工兜底。

1. `header_row()`：只扫前 30 行 × 前 120 列，按「非空字符串单元格数」打分取最高分的行。
2. `label_text()`：数字、以 `=` 开头的公式、日期值、空白、超过 `MAX_MODEL_TEXT_LENGTH = 80`
   的文本一律不算表头字段。
3. `date_axis_cells()`：先收集日期单元格，若同行/同列有"日期"字样则直接返回；否则要求连续
   日期 ≥ 3 个且相邻间隔天数的极差 ≤ 3 天才认定为日期轴（且 `<2` 个日期直接返回空）。
4. `call_model()`：用完整语义链（文件名→Sheet→父级标签→字段→日期）比较，禁止纯文字相似匹配，
   `confidence < 0.9` 的规则不输出；`append_rows` 与 `metric_fill` 两种结构分开处理。
5. 人工修正走**坐标**校验：`direct_coordinate_correction_plan()` + `norm()` 精确匹配。

**已知坑**：`header_row()` 只看"字符串个数"。若某个数据行的文本单元格比真表头行还多，
它会误选那一行（已构造用例复现：真表头 3 个字段、数据行 8 个文本 → 选中数据行）。
真出现时让用户在"识别表头位置"里手动指定字段修正。

### 「识别表头位置」按钮的候选来源（`POST /api/sheet-fill/inspect`，不调用模型）

`profile_field_options()` 把 profile 摊成左右两个下拉，**两侧规则不对称**——这是关键：

- **左侧「数据源字段」**：来自 `source_profile()`。每个**可见** Sheet 用 `header_row()` 打分选出
  **唯一一行**表头，字段 = 该行通过 `label_text()` 的单元格。坐标 = 列字母 + 表头行号。
  label = `文件名 / Sheet / 坐标 / 字段名`。
- **右侧「待填表格字段」**：来自 `template_profile()` 的 `table_header_candidates`，
  **不做打分**：前 30 行里文本标签 ≥ 2 个的行**全部**成为候选（标题行、真表头、有文字的数据行
  都会进来）。坐标 = `cell.coordinate`。label = `Sheet / 坐标 / 字段名`。
  待填表用 `data_only=False` 读，公式以 `=` 开头会被 `label_text()` 排除。

提交填充时会**重算一遍** profile，再用 `(文件, Sheet, 坐标, 字段名)` 校验选项，对不上就报
"待填表格修正位置已失效，请重新识别字段"，所以识别结果是**一次请求一版**，不能跨文件复用。
左右都选 → 纯坐标生成 `append_rows` 规则（`confidence=1`，不经模型）；
只选右侧留空左侧 → "定点重新匹配"，**必须启用 LLM**。

`webapp/api/main.py:100` 导入的 `direct_header_correction_plan` 已无调用点（死导入），
现行路径是 `direct_coordinate_correction_plan`。

### 横向/纵向对齐靠 orientation，不做转置

全项目**没有任何 `transpose`**。`apply_plan()` 的 `metric_fill` 分支用「日期方向」把两侧解耦：

- `source_orientation`：`vertical` 时 `header_row()` + `find_header()` 定位日期列/数值列，从
  `hr+1` 往下逐行读；`horizontal` 时定位日期行/数值行，从第 1 列往右逐列读。
- 两种方向都归一化成同一中间层 `records = [(起始日, 结束日, 数值), ...]`。
- 模板侧按 `target_orientation` 对称处理：`horizontal` 沿列扫目标指标行，`vertical` 沿行扫目标指标列。
- 因此**源横向 + 模板纵向（或反向）都能填**，单元格物理位置从不移动。
- 已实测：横向源表（日期行 1 / 数值行 2）→ 纵向模板，`direct` 正确写出 B2=10、B3=20。

`aggregate()` 的安全设计（别误以为是 bug）：
- `direct` 只在恰好命中 1 条记录时返回，多条返回 `None` → 不猜。
- 筛选条件是「记录区间完整包含于目标区间」(`first >= start and last <= end`)，
  跨边界的记录**整条丢弃**，不按天拆分。
- `apply_plan()` 只写原本为空的目标格；已有值的一律记入 `protected_cells` 不动。
- 填充前、填充后、保存后三次比对全部公式集合，任何变化即抛错并删除输出文件。

## 实测案例：浪琴品牌周报模板把候选表头认到第 12 行

文件：`/Users/geng/Desktop/表格agent/浪琴品牌周报内容20260910_副本.xlsx`（4.4MB）。
用户截图里 `9-内容数据 2 / A12 / 渠道` 这类三项式标签（`Sheet / 坐标 / 字段名`）= **「待填表格字段」**
（模板侧 `template_profile()`），不是数据源侧（那是四项式 `文件名 / Sheet / 坐标 / 字段名`）。

- 该表第 1 行是 13 条说明文案，长度 408～692 字符，**全部超过 `MAX_MODEL_TEXT_LENGTH = 80`**
  被 `label_text()` 过滤 → 字段数 0 → 落选。
- 第 12 行是真表头，29 条短标签（渠道/数据·规划/日期/TTL/环比…）→ ≥2 → 进候选，坐标 A12…DP12。
- 该表候选行共 5 个：`[12, 13, 19, 23, 26]`，全部并入同一个下拉（三张表合计 113 项）。

**发现的两处不对称（待与用户确认是否要改）：**
1. `template_profile()` **不过滤隐藏工作表**，`source_profile()` 过滤（`sheet_state != "visible"` 就跳过）。
   本例中三张表名字极像（`9-内容数据2 ` 1407 列 / `9-内容数据  ` 1695 列 / `9-内容数据 ` 21 列），
   前两张是**隐藏**表。结果：隐藏表能当待填模板，却不能当数据源，下拉里混入大量噪音。
2. 已能通过 `webapp/local_agent` 的 editor_sdk（`edsdk.py`，端口 39099+）读本地表格，
   `open_file` 返回的 `file_id` 就是文件绝对路径。
